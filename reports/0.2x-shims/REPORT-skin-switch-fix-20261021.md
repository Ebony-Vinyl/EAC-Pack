## 1. 已修复：entry id 与皮肤管理器不匹配

### 归属：**我们自己的代码**

问题出在 `EAC-Pack/scripts/repack/ensure-bundles.mjs`，不是上游、也不是内核。

该脚本给「上游漏带 `dsh.bundle.patch` 的包」补一个自挂载 patch，原实现用的是
catalog 的 `entry.id`：

```js
- id: ${entry.id}          // → blue-fantasy
```

而皮肤管理器写 `cordis.patch.yml` 的 managed 段用的是 **`skin.json#wiring.id`**：

```yaml
- id: ui-skin-blue-fantasy
  disabled: true
```

同一个包声明两套 id：

| 字段 | 值 | 谁在用 |
| --- | --- | --- |
| `skin.json#id` | `blue-fantasy` | 目录/展示 |
| `skin.json#wiring.id` | `ui-skin-blue-fantasy` | **cordis loader 的真实 entry id** |

`cordis-plugin-loader` 按 **entryId** 匹配 `disabled`，匹配不到就什么也不做 ——
于是 `blue-fantasy` 那行 `disabled: true` 打在了一个不存在的 entry 上，皮肤永远启用。

### 为什么只有它出问题

12 个皮肤包里，11 个的 `cordis.patch.yml` 是**上游自带**、且都用 `ui-skin-*`；
只有 `blue-fantasy` 0.2.0 上游漏带，被我们补 —— 补的时候用了错的 id。
**这条路径只在「我们替上游补 patch」时才走到，是最容易漏的一类。**

### 修复

`ensure-bundles.mjs` 改为优先读 `skin.json#wiring.id`，回退 `entry.id`；
并新增「纠正旧产物」分支 —— 因为早期版本一旦补过 patch，该包就带上
`dsh.bundle.patch`，后续会被 `continue` 跳过，错误产物永久固化。

### 实机验证

| 阶段 | 结果 |
| --- | --- |
| dist 产物 | patch id 从 `blue-fantasy` → `ui-skin-blue-fantasy` |
| 装回变体 profile | 装前 `blue-fantasy`，装后 `ui-skin-blue-fantasy` |
| 重启后 loader entry | `include:ui-skin-blue-fantasy` **disabled**（修复前是 `include:blue-fantasy` ENABLED） |
| 11 项 managed 段 | 全部 `disabled: true`，与配置**逐条一致** |

### 回归测试

`suite/test/artifact-loadable.test.mjs` 新增一条：

```
皮肤包 bundle patch 的行 id 必须等于 skin.json 的 wiring.id
```

- 正向：12 个皮肤包全部对齐 → PASS
- **反向验证**：手工把 tgz 的 id 改回 `blue-fantasy` → 测试精确报错
  ```
  blue-fantasy: patch id "blue-fantasy" ≠ wiring.id "ui-skin-blue-fantasy"
  ```
  恢复后回到全绿。测试有判别力，不是空跑。
- 全量套件：**102/102 pass**（原 101，新增 1）

## 2. 剩余问题

启动后实测 loader entry 启用状态：

```
ENABLED   include:skin-switch                  ← 切换器本身，不该被管
disabled  include:ui-skin-deep-whale-day-night
disabled  include:ui-skin-blue-fantasy         ← 本次修好的
disabled  include:ui-skin-dragon-heir
disabled  include:ui-skin-miku
disabled  include:ui-skin-minecraft
disabled  include:ui-skin-qq98
disabled  include:ui-skin-ths
disabled  include:ui-skin-trading
disabled  include:ui-skin-whale-song
disabled  include:ui-skin-xp
ENABLED   include:ui-skin-deep-whale-manager   ← 管理器本身，不该被管
ENABLED   include:ui-skin-maid-atelier         ← 应可控，但不在 managed 段
disabled  include:ui-skin-orca-link
ENABLED   include:liang-intensity-skin         ← 应可控，但不在 managed 段
ENABLED   include:theme-endfield               ← 应可控（若不并入皮肤体系）
```

### 2.1 三个皮肤不在 managed 段

`ui-skin-maid-atelier`、`liang-intensity-skin`、`theme-endfield` 启用但**从不出现在
managed 段**，所以界面点了也改不了它们。

- `ui-skin-maid-atelier` 的直接原因：`skin.json` 的 `id` 被
  `@dsh-external/dsh-client-ui-skin-deep-whale-day-night` 抢先占用（两者都是
  `id: "maid-atelier"`），`discoverInstalledSkins()` 按 `ids.has(entry.id)` 去重后丢弃它。
- `liang-intensity-skin`、`theme-endfield` **没有 `skin.json`**，管理器按设计认不出它们。

这两类都需要**扩大管理器的识别范围**，属于我方 adapter 的适配决策，不是上游 bug。

### 2.2 切了不会立刻生效

实测：`POST /api/dsh/skins` 返回 200、两层文件都正确落盘，但**运行中的 loader
entry 不变**，必须**重启实例**才生效。

管理器前端在成功后 1.2 秒调用 `window.location.reload()`，那只是刷新浏览器，
不重启 host 进程，所以 loader 不会重新读 patch。

### 2.3 `bodyAttr` 多重挂载（互斥仍然失效）

`tools/audit-skin-exclusivity.mjs` 实测：配置为「官方」时，`<body>` 上仍有

```
data-dsh-blue-fantasy, data-dsh-maid-atelier
```

原因：客户端 bundle 的取舍由 `dsh.profile.bundles`（61 项）决定，
`cordis.patch.yml` 的 `disabled` 只影响 **host 侧插件**，不影响客户端发包。
每个皮肤 client.js 加载即执行、各自给 body 加属性。

而管理器判「当前皮肤」用的正是 `document.body.hasAttribute(bodyAttr)`，
所以属性集合不变 → 界面永远显示同一个。

## 3. 归属汇总（回答「要不要联系上游」）

| 问题 | 归属 | 依据 |
| --- | --- | --- |
| entry id 不匹配 | **我方 `EAC-Pack/scripts/repack/ensure-bundles.mjs`** | 文件首行 `# Self-mount bundle generated by eac-plugin-suite` |
| mangler 认不出无 `skin.json` 的皮肤 | 我方适配范围 | 管理器遍历 `dependencies` + 只认 `skin.json` |
| `maid-atelier` id 冲突 | **上游两个包之间** | 两个 `skin.json` 都写 `id: "maid-atelier"` |
| 客户端 bundle 不看 `disabled` | **上游内核设计** | `@deepseek-ai/dsh-client-modules` 取 host Loader entries；`@deepseek-ai/cordis-plugin-loader` 按 entryId 判 disabled |
| 切换需重启 | 上游设计 | 管理器注释原文「A service restart is required for the new row set to take effect」 |

**结论：本次修的这一条完全在我们自己仓库里，不需要联系任何上游。**
剩余 2.1/2.2/2.3 里，只有 `maid-atelier` 的 id 冲突需要上游改，其余都是我方适配或上游既定设计。
